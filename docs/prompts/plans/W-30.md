# W-30 design note: XML route for inbox adds and copies (item 8), build source check (item 10)

Written 2026-10-21 before the build. Brief: `docs/prompts/W-30.md` with `W-30b.md`. Checked against CLAUDE.md's hard rules.

## Item 8: `dj apply --xml`, `dj copy --xml` (Q-22, R-802)

- Flow: dry-run (snapshot read, R-202) prints the preview id, as today; the dry-run does not depend on the mode, so one preview id serves `--xml` and `--power-mode`. `--apply --xml --preview-id <id>`: a fresh snapshot read recomputes the changes, `write_gate.check` compares them with the preview (same kind `apply` / `copy`, same args), then `proposals/<crate-slug>-adds-<date>.xml` is written: one top-level playlist `<crate leaf> adds <date>` holding the approved tracks in plan order (copy: source order), each track's location from the library (snapshot `DjmdContent`, `readers.db.to_track`), through `writers.rekordbox_xml.plan_lists` / `render` / `write_xml` (create-only: `-2`, `-3`).
- Never a write session: `--xml` calls no `safety.open_db(write=True)`, no backup, no process check; works on every OS, needs no `--power-mode`. `--xml` with `--power-mode` is refused (two write paths, pick one). db mode is unchanged: Windows power mode, re-plan inside the write session.
- Where: the library folder's `proposals/` when the inbox loop runs there (`intake.default_paths().library`; the scaffold's `.gitignore` already holds `proposals/*.xml`), else the repo's `proposals/` (new `/proposals/` line in the repo `.gitignore`: the XML holds paths from this computer). Copy follows the same rule.
- After the XML: the preview id is consumed (`written` = the XML), apply records the decisions as db mode does (yes picks -> match memory, no -> declined; nothing re-asked) and its report says `in_xml` (and `left_out`: no file location) instead of `added`; copy writes its report with `xml`. One `log.md` line: `apply <crate> as XML -> N in XML, ...; proposals/<file>.xml` / `copy <a> to <b> as XML -> ...`.
- Reply: `xml`, `playlist`, `import_steps` = steps 1-2 of `build_structure.import_steps` for the device (library.yaml `device`, else this OS; a new keyword `folder` names where the file sits) plus step 3, the one drag: select all tracks of the imported playlist and drag them onto the crate.
- MCP: `dj_apply_write` / `dj_copy_apply` take `mode` (`"xml"` | `"db"`; empty = `db` when `power_mode=true`, else `xml`, so XML stays the default path, rule 4). `db` needs `power_mode=true` (refused before anything runs); `xml` refuses `power_mode=true`. The preview id check is the CLI's, identical in both modes.
- Hard rules: create and add only (a new XML file, create-only; rekordbox changes only when the DJ imports and drags); dry-run default (`--apply` + the previewed id, nothing without it); master.db never opened for writing in xml mode, read only from a snapshot; nothing personal in the repo (the repo-root XML is gitignored).

## Item 10: build source check (Q-17)

- `structure/proposals.yaml` gets `source` per proposal entry (optional key on load, so older files still read): the export it was made from, library-relative (`exports/<date>-collection.xml`), or for a db read `master.db (snapshot read <ISO time>)`.
- `dj-build` preview and apply block (no preview id; apply refuses) when the entry names an export that is no longer in the folder, when the export dj-build reads is older (mtime) than the named export, or, for a db source, older than the snapshot read. The line ends "Export again, then say the trigger prompt." No `source` (hand-made proposal, older file): no check.
