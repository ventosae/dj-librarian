# W-21 design: the write gate everywhere, power mode, the hook, the engine card

R-102, R-205, R-1101, R-1102, R-1105, C-10. Checked line by line against the CLAUDE.md hard rules.

1. **One gate module.** `dj.write_gate` (stdlib only) wraps `dj.gate.Gate(REPO_ROOT / "state")`: `digest(changes)` = sha256 of the canonical JSON of what a write would do; `record`, `check`, `consume`, `require_id`, `require_power_mode`. Kinds = the command: `tree`, `apply`, `copy`, `push`, `build`, `tidy-apply`, `tidy-undo`.
2. **Rule 2 (preview, then an explicit yes).** Each dry-run computes its plan as today, records it (args = normalised arguments: resolved paths, flags, the effective Spotify name) and prints `Preview id: <id>` (`--json`: key `preview_id`). A plan holding a CONFLICT (`dj tree`) gets no id. `--apply` needs `--preview-id`: missing, malformed, another command or arguments, older than 24 h, used, or a plan whose digest changed -> exit 1, one line `REFUSED <reason>`. The digest is recomputed in the write path from a fresh read before the backup (DB), before the write token and first Spotify write (push, build), before the first file write (tidy). The id is consumed only after something was written; a no-op apply, or a tidy run where every item failed, leaves it unused. A dry-run of a plan whose id was used gets a fresh id (`Gate.record(rearm=True)`, generation n): the DJ can undo a write (rows removed in rekordbox, the Spotify playlist deleted, `dj tidy undo`) and the same plan stays writable, as before the gate; a replay of the used id stays refused. Push/build run every check but the digest (`write_gate.precheck`) before any token request or Spotify call.
3. **Digests (the planned changes).** tree: the CREATE actions (kind, path, rules). apply: crate + adds (uri, pick) + yes picks + no uris (the write also records decisions). copy: source, target, content ids to add. push/build: Spotify name (+ rekordbox playlist id) + selected uris. tidy apply: the ready items (file, sha256, changes, rename). tidy undo: the records it would restore (seq, files, sha256_after).
4. **Rule 3 (closed rekordbox, verified backup, one commit, rollback).** Unchanged: `safety.open_db(write=True)` still does the process check, the verified backup, one commit, rollback. The gate runs before it, so a refusal takes no backup. Inside the write session the plan is re-planned (as today) and compared with the checked digest before the first create/add: a mismatch raises, open_db rolls back.
5. **Rule 4 (XML default, DB writes Windows power mode behind a flag).** `dj tree|apply|copy --apply` also need `--power-mode`; checked first (before the preview id, before any read or backup). Without it: `REFUSED master.db writes are power mode (Windows only): add --power-mode, or build an XML to import (dj library build)`. Off Windows (`safety.DB_WRITE_PLATFORMS`) the same up-front check refuses in one line even with the flag; open_db's own refusal stays as a second wall and is printed as one line, never a traceback.
6. **Rule 1 (create and add only), rule 5 (idempotent).** No new mutating call; the write paths are the existing ones.
7. **Rule 6 (secrets).** Push/build ask for the read scopes for matching and the write scope only after the gate passed; a refusal requests no write token.
8. **MCP.** Preview tools pass `preview_id` through (it is in the CLI JSON; `dj tree --json` carries it). Write tools take a required `preview_id` (12 lower-case hex, else `{ok: false, error}` before any run) and pass `--preview-id`; the three master.db tools take `power_mode` (default false, refused without it, checked first). New READ tool `dj_tidy_undo_preview`. Push/build/tidy previews gain `name` / `include_ambiguous` / `strict` so the preview's arguments can match the write.
9. **The hook (C-10, Claude Code only).** `plugin/hooks/hooks.json`: PreToolUse, matcher `^mcp__(plugin_dj-librarian_dj-librarian|dj-librarian)__[A-Za-z0-9_]+_(apply|write|undo)$` (also catches `dj_structure_write`, `dj_crate_write`). `gate.py` (stdlib) denies through `hookSpecificOutput.permissionDecision: "deny"` when `tool_input.preview_id` is missing or not 12 lower-case hex; else exit 0, no output. Unreadable input: deny unless a tool name in it is plainly not a write tool.
10. **Why uv runs the hook.** The DJ has no system Python on Windows; macOS's `/usr/bin/python3` is a stub that opens an install dialog. The engine already needs `uv` (`.mcp.json` runs `uv run`), so `uv` is on every machine where the write tools exist. Exec form (`command: "uv"`, `args: [...]`): no shell, so the same entry works on Windows and macOS with no quoting of `${CLAUDE_PLUGIN_ROOT}`. `--no-project` skips project discovery (fast, no venv needed); `--python ">=3.9"` overrides a `.python-version` in the DJ's working folder, so no download for an odd version. `onFailure: "block"` makes the gate fail closed: no uv, a crash or a timeout blocks the write instead of letting it through.
11. **Cowork (Q-03).** Hooks are not a Cowork component: there the gate is "ask every time" on every write tool + the XML the DJ imports. `docs/permissions.md` lists read, library-text and write tools with the setting for each.
12. **M1 card (R-102, R-1101).** `plugin/skills/dj-start/engine.md`: offered only on "set me up" or when a feature needs live data; about 10 minutes; 3 steps for the DJ's OS (install uv, get the engine + enable the connector + `dj library use <folder>`, write tools on ask-every-time); proof = `dj_status` answers with the track count. New CLI `dj library use <folder>` (remember_root; an unusable `DJ_LIBRARY` refuses before anything is stored).
13. **Q-08 (open).** `.mcp.json` runs `uv run --directory ${CLAUDE_PLUGIN_ROOT}/..`: that is the clone only when the plugin loads in place. Claude Code loads a relative-path plugin from a marketplace added from a local folder in place, so the card's Claude Code line is `claude plugin marketplace add ./` (in the clone), then `claude plugin install`. A GitHub marketplace or a zip upload runs from a cached copy with no engine next to it. Which Cowork add path keeps the plugin in place is unverified: the card says so and points a Cowork DJ at the README's manual registration when `dj_status` does not answer. R-102 stays blocked on Q-08 for Cowork.
14. **Tests.** Per CLI write command and per MCP write tool: dry-run returns an id and writes nothing; apply without id, wrong id, changed plan, used id -> refused with no backup, no `open_db(write=True)`, no write token, no audio file touched; power-mode refusals; success with the right id. Hook: subprocess payloads + matcher vs full tool names.
