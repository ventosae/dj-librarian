# W-34 design note: the engine as an MCPB desktop extension

Written 2026-10-24 before the build. Brief: `docs/prompts/W-34.md`. Spec read: modelcontextprotocol/mcpb MANIFEST.md (0.3 header, `uv` type "v0.4+"), README, CLI.md, `examples/hello-world-uv`; claude.com/docs/connectors/custom/add-unlisted; code.claude.com/docs/en/plugins-reference.

## Facts found before building

1. **A plugin carries a bundle through `plugin.json`, not `.mcp.json`.** The plugin reference: `mcpServers` takes "a `.json` file path, an MCP bundle path or URL, an inline map"; a bundle path ends in `.mcpb`, and Claude Code extracts it into `.mcpb-cache/` under the plugin root. `.mcp.json` holds only a server map. So `plugin.json` gets `"mcpServers": "./engine.mcpb"` and `plugin/.mcp.json` goes.
2. **Claude Code 2.1.299 refuses a `uv` bundle inside a plugin.** Prototype in a scratch copy of `plugin/`: `claude plugin validate ./plugin --strict` passes, but loading logs `Invalid manifest: server: Invalid enum value. Expected 'python' | 'node' | 'binary', received 'uv'`; the skills still load (12). The same bundle relabelled `python` loads, is extracted, and Claude Code reads the bundle's own `user_config` ("requires user configuration; MCP server "dj-librarian" not started. Configure via: /plugin → Installed → dj-librarian → Configure"). So the bundle's `user_config` needs no copy in `plugin.json`.
3. **Only `uv` can run without uv on the DJ's machine** (the host manages Python and the dependencies). `python` with `command: uv` needs uv on PATH. We keep `uv` in both places; the one-upload route waits for a host that accepts `uv` in a plugin. Q-31 records this.
4. **The layout runs.** The prototype bundle (manifest, `pyproject.toml`, `uv.lock`, `.python-version`, `LICENSE`, `README.md`, `src/dj/**`; 64 files, 448 KB), unpacked and started as the manifest says (`uv run --directory <dir> --no-dev --frozen dj-mcp`), answers `initialize` and lists 30 tools.
5. No Node on the build machine: `scripts/build_mcpb.py` writes the zip itself (the spec: a zip with `manifest.json` at the root); `--npx` uses `npx @anthropic-ai/mcpb pack` when Node is there.

## Manifest (`mcpb/manifest.json`)

- `manifest_version` `0.4` (the `uv` type), `name` `dj-librarian` (the server key, so tool names and the write-gate hook matcher stay `mcp__dj-librarian__*` / `mcp__plugin_dj-librarian_dj-librarian__*`), `display_name` `dj-librarian engine`, `version` = `pyproject.toml` = `plugin.json` (test).
- `server`: `type` `uv`, `entry_point` `src/dj/mcp_server.py` (it has `if __name__ == "__main__"`), `mcp_config`: `command` `uv`, `args` `["run", "--directory", "${__dirname}", "--no-dev", "--frozen", "dj-mcp"]`, `env`: `DJ_LIBRARY` ← `${user_config.library_folder}`, `SPOTIFY_CLIENT_ID` / `SPOTIFY_CLIENT_SECRET` ← the sensitive strings, `DJ_POWER_MODE` ← `${user_config.power_mode}`, `DJ_ENGINE` = `mcpb`.
- `user_config`: `library_folder` (directory, required), `spotify_client_id`, `spotify_client_secret` (string, sensitive, optional), `power_mode` (boolean, default false).
- `compatibility`: `platforms` `darwin`, `win32`; `runtimes.python` `>=3.12` (pyproject). `tools`: the 30 MCP tools, names equal to what the server registers (test). `privacy_policies`: Spotify's, since the engine calls the Spotify Web API with the DJ's own app.

## Engine environment (all Door 2; the clone keeps today's behaviour)

- One reader for host-given values: empty, or an unsubstituted `${...}`, counts as unset (a host may pass either for an empty optional field).
- `DJ_LIBRARY`: the library folder (already read by `libfolder.configured_root`).
- Config files `tidy.yaml`, `bases.yaml`, `tree.yaml`, `links.yaml`, `library.yaml`: the library folder first, the repo root as the clone's fallback.
- Spotify keys: `SPOTIFY_CLIENT_ID/SECRET` from the environment first, then the library's `.env`, then the repo's `.env`.
- `DJ_POWER_MODE`: set and false → every master.db write refuses, whatever the call says ("power mode is off in the engine settings"); true or unset → today's rule (the explicit flag, Windows only, preview id).
- `DJ_ENGINE=mcpb`: the code root is the extension's install folder, which an update replaces. State that must outlive an update moves to `<library>/.cache/engine/` (preview records, build/push state, the Spotify token, caches, master.db backups); reports go to the library folder. Without a usable library folder: `~/.dj-librarian/`.

## Plugin and builds

- `plugin/engine.mcpb` is a build product (gitignored). `scripts/build_mcpb.py --plugin` writes it there; `claude plugin validate ./plugin` needs it, so CI builds it first.
- `scripts/build_plugin_zip.py` puts the engine in the zip by default (≤ 15 MB check); `--no-engine` leaves it out and drops `mcpServers` from the zipped `plugin.json`, so the light zip still validates.
- `userConfig.uv_path` and the `--directory ${CLAUDE_PLUGIN_ROOT}/..` command go.
- `release.yml` attaches `dj-librarian-engine-<v>.mcpb`, `dj-librarian-plugin-<v>.zip` and `dj-librarian-plugin-<v>-no-engine.zip`.

## Known gap, not in this PR

- The write-gate hook (`plugin/hooks/hooks.json`) still starts `uv`. On a machine without uv it fails closed in Claude Code (write tools denied). Logged with Q-31.
